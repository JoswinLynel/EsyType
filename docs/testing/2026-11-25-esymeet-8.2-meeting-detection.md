# EsyMeet 8.2: meeting detection and the "Meeting detected" prompt. Test record

**Date:** 25 November 2026 · **Plan:** `docs/plans/esymeet-8.2-meeting-detection-plan.md` (approved by the owner, all eight defaults) · **Build:** e2e test build only · **Production: not changed** (0.5.1 stays installed; 8.2 is released together with 8.3, owner decision 1) · **Nothing downloaded; no dependency added**: four more feature flags of the `windows` crate already in use (audio sessions, process information)

## 1. What was built

- **Detection** (`src-tauri/src/meeting_detect.rs`):
  - Every 2 s, EsyType asks Windows which programs have an **active microphone stream**: the audio sessions on each microphone.
  - It counts only programs on the **meeting allow-list**: Teams (new and classic), Zoom, Webex, Slack, Skype, GoTo Meeting, RingCentral, Discord, Chrome, Edge, Firefox, Brave, Opera and Vivaldi.
  - **Never counted:** EsyType itself, or anything else that uses the microphone (dictation apps, recorders, games).
  - **WebView2 apps:** for apps built on WebView2, such as the new Teams, the helper process is followed up to the app that started it.
  - Only program file names are read.
- **The rules** (pure functions, unit-tested):
  - the microphone is used for at least 5 s before a prompt
  - one prompt per call
  - Not now holds until that app lets go of the microphone
  - the prompt goes when the call ends, or when the app or detection is switched off
  - two apps at once: one prompt, naming the first
  - an unanswered prompt fades after 30 s
- **The prompt:**
  - a capsule like the pill (light frost), at the top centre
  - "Meeting detected · <app>" and "Let people know you're transcribing.", with **Start transcription** and **Not now**
  - it never takes the keyboard, and is announced to screen readers
- **Start transcription:** opens the EsyMeet page and sends the event the recording session (8.3) will start from.
- **Tray:** a new item, **Start meeting transcription**. It's greyed out except while a meeting app holds the microphone.
- **Settings ▸ Meetings** (new section):
  - **Detect meetings** (on by default)
  - a switch per app (Discord off by default)
  - what EsyType reads, and that nothing is recorded until Start
- **New settings:** `meet_detect` (true) and `meet_off` (["discord"]). Older settings files take these defaults.
- **Pill and prompt are raised to the top of the always-on-top windows when shown,** without taking focus. Without this, a window shown on top earlier can cover them, as a meeting app's small call window would. Seen in testing: a test window covered the prompt.

## 2. Change from the plan, measured

**The plan named Windows' privacy record in the registry** (`CapabilityAccessManager\ConsentStore\microphone`). On this PC (Windows 11 build 26300) that record **had not been updated since 27 September 2026**: Wispr Flow, EsyType's own dictations and today's test program were all missing. It cannot say what is in use now.

So detection asks Windows' **audio session manager** instead: a documented interface, which lists the programs with an active capture stream right now.
- **Measured live:** while the test program used the microphone, it was the only capturing process, and it was recognised.
- **The behaviour and all eight defaults are unchanged.**
- The plan's own risk ("Windows changes the record") is what happened; the replacement doesn't depend on that record.

**The check runs every 2 s,** as the plan's "every 2–3 s", rather than 1 s: at 1 s the watcher cost 0.7% of one core (section 4).
