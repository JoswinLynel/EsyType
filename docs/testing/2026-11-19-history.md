## Problems found and fixed

| # | Problem | Fix | Verified by |
|---|---|---|---|
| 1 | Deleting one entry, an expiring entry, an edit or turning off "keep the original" could leave the old text readable in the database's write-ahead log (`esytype.db-wal`) until SQLite next tidied it | The log is flushed into the (secure-delete) database and emptied after each of these | New unit test `removed_text_leaves_no_trace_in_the_files`; it fails without the fix |
| 2 | Entries that expired while EsyType sat idle stayed visible until the next dictation or restart | Expired entries are removed whenever History is opened | Section 3 |
| 3 | **Test builds switched off the owner's real "start with Windows".** They share EsyType's startup name and applied their own test setting (off), deleting the owner's registry entry; a Windows restart would not have started EsyType | Test builds never touch the Windows startup setting. The owner's entry was restored by restarting EsyType | Entry checked present after a full test run (section 5) |
| 4 | Test builds could not run while the owner's EsyType was open (single-instance handed off) | Test builds have their own app identity | All runs in this record |

**Owner note on 3:** between about 10:50 and 11:30 on 19 November the owner's startup entry was missing at times. If Windows was restarted in that window and EsyType did not start, this was the reason. It is in place now.
